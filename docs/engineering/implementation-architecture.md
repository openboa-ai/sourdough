# Implementation architecture

**Scope:** a local company that can complete its first Agent-originated paper trade with the Board Client absent and scale across all company, quant, control-plane, change-management and learning flows under one unified runtime and storage kernel. This document fixes how modules fit together. The [responsibility map](../company-agent-quant.md) names the owners; each [unit spec](work-packages.md) defines its behavior. Design is not evidence of a working system.

## What runs where

```text
Human → Board Client (apps/board, Zig) ──► Local UDS Control Plane (/v1/*)
                                                  │
┌─ Sourdough CompanyRuntime (single local daemon under WriterLease) ────────┐
│ Control Plane: peer cred + board_binding + scoped roles → command_receipt │
│ Unified Scheduler: DutyRegistry + 3-entity Work kernel (items/runs/conds) │
│ Two-Plane Agent Harness: Outer Capability Broker ↔ Inner Sandboxed Desk   │
│ Domain Services: Org, Authority, Work, Comms, Assets, Finance, GL, Ops,   │
│                  Optional Quant Profile (Research, Risk, Subledger, Perf) │
│ Authoritative SQLite Store (WAL, STRICT, ordered migrations, audit_event) │
└───────────────────────────────────────────────────────────────────────────┘
Harness Host ↔ pinned runtime adapter ↔ Agent runtime (judgment, no DB access)
Fund ↔ outbox / connector ↔ Separate Managed Paper Venue Process (paper_sender_lease)
Evaluator ↔ Physically Separate Evaluator SQLite Store (out-of-band Flows 12–13)
```

The entry point wires enabled modules into one local Python `CompanyRuntime` daemon supervised under `WriterLease`, replacing separate per-scenario worker loops. Within the service, call the owning module's typed operation directly. Domain decisions take typed values; they do not import UI code, SQL rows or a provider SDK. The consumer defines the narrow interface it needs; the SQLite, Agent or venue adapter implements it. Only add an interface where an effect, a second implementation or an independent test requires one. No internal HTTP hops, generic repository per table, or external message broker.

The base company can start and assign work without the fund profile. The fund may call company capabilities; company work does not import order types. A conversation can notify another Agent, but only an [accepted handoff](../company/systems/work/collaborate/handoff/spec.md) changes the duty owner. Likewise an Agent can request a trade, but cannot write a position. These rules hold even when modules share a process.

### Unified runtime and two-process paper venue

- **Unified `CompanyRuntime` and `DutyRegistry`:** Every scheduled unit executes through one durable queue (`work_runs`) and a pure `DutyRegistry` mapping `duty_kind` (`work.execute`, `work.peer_review`, `org.staffing`, `org.onboarding`, `quant.research`, `quant.paper_decision`, `quant.window_close`, `quant.challenger_eval`, `ops.reconcile`, `ops.change_qualify`, `learning.distill`) to precondition, authority scope, budget envelope, harness profile and completion/failure transitions.
- **Three-entity Work kernel:**
  - `work_items` owns durable duties, ownership and disposition.
  - `work_runs` owns execution claims with partial unique indexes permitting at most one active `running` run per `agent_id` and per `work_item_id`, monotonic `fencing_token` incremented on every claim and verified on every domain write, an **anti-self-wake** rule (an Agent's own message or status comment never wakes that Agent), and **zero-compute durable waits** (`status = 'waiting'` with `wait_until_ns` or `wait_event_key`, releasing execution slots until due time or a matching domain event).
  - `work_responsibilities` and `work_conditions` own standing responsibilities and time/event triggers with `condition_revision` and `(source_identity, condition_revision)` deduplication before creating eligible work.
- **Two-process paper venue boundary:** The company-managed paper execution worker (pinned `nautilus_trader==1.231.0`) remains in a **separate process** from `CompanyRuntime`, protected by `paper_sender_lease` and bounded rotating activation segments (8–600 seconds) with explicit drain margins. Loss or restart of `CompanyRuntime` never wipes the venue journal, and startup recovery reconciles `in_flight` `external_actions` by original `idempotency_key` before admitting new risk.

## SQLite storage kernel and migrations

- **Single-writer connection (`open_writer`):** Open via Python 3.14 `sqlite3.connect(path, autocommit=True)` only after verifying `WriterLease` and confirming the store is not retired. Set `PRAGMA busy_timeout` **before** enabling `PRAGMA journal_mode=WAL`, then apply `PRAGMA synchronous=FULL`, `PRAGMA foreign_keys=ON`, `PRAGMA trusted_schema=OFF`, `PRAGMA journal_size_limit`, and `PRAGMA temp_store=MEMORY`. Every mutation runs inside an explicit `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK` block.
- **Read pool (`open_reader`):** Open with URI `mode=ro` and `autocommit=True`, applying `PRAGMA query_only=ON`, `PRAGMA trusted_schema=OFF`, `PRAGMA foreign_keys=ON`, and `PRAGMA busy_timeout`. Keep read transactions short and close them immediately to prevent WAL checkpoint starvation.
- **Unified ordered SQL migrations:** Replace ad-hoc `CREATE TABLE IF NOT EXISTS` growth with immutable, checksummed SQL migration files tracked in `schema_migrations` (`version`, `domain`, `name`, `sha256`, `applied_at_ns`) and stamped into `PRAGMA user_version` in the same transaction. Provide a deterministic one-time upgrade path from legacy v1–v7 stores into the unified baseline. Opening a store whose `PRAGMA user_version` exceeds the running binary's maximum supported schema version **fails closed**. Declare kernel and domain tables `STRICT`.
- **Kernel audit, receipts and outbox:** Every state-changing transaction atomically commits (1) authoritative domain table changes, (2) `command_receipt` finalization (including persisted `conflicting_revision` denials and typed multi-field `preconditions_json` when control-plane initiated), (3) append-only `audit_event` rows protected by `BEFORE UPDATE` and `BEFORE DELETE` abort triggers, and (4) `external_actions` outbox entries for effects executed strictly outside the write transaction.
- **WAL checkpointing, backup normalization and logical cut verification:** Run periodic `PRAGMA wal_checkpoint(PASSIVE)` during runtime maintenance and `PRAGMA wal_checkpoint(TRUNCATE)` with `PRAGMA optimize` on clean shutdown. Both checkpoint snapshots and shadow-staged restores MUST normalize the staged SQLite file to `PRAGMA journal_mode=DELETE` with **zero `-wal` or `-shm` sidecars** before publish, verify `quick_check`, `foreign_key_check` and `fsync`, and verify cut equivalence via a **logical watermark** (`company_id`, `schema_version`, `max_event_seq`, canonical domain digest) rather than raw file byte SHA-256.

## Interfaces and trust

- **Human and Local UDS Control Plane:** The daemon exposes a versioned HTTP/1.1 + JSON + NDJSON API over a local Unix domain socket (`/v1/meta`, `/v1/projections/{name}`, `/v1/events`, `/v1/commands`, `/v1/commands/{command_id}`), bound **only while holding `WriterLease`**, in a `0o700` user-private directory with `0o600` socket permissions and a macOS path strictly under 104 bytes. Every connection verifies kernel peer credentials (`LOCAL_PEERCRED`/`LOCAL_PEERPID`) combined with an explicit company-enrolled `board_binding` and scoped [role assignments](../company/systems/authority/authorize-actor/manage-roles/spec.md) (`board_viewer` vs `board_control`; fail-closed when unbound). A local connection alone is never identity or authority.
- **Projections and commands:** `/v1/projections/{name}` serves ACL-filtered on-demand `open_reader()` indexed queries (preserving `work-timeline-v1` content-hash `revision` while adding `ETag` and `event_seq` on `work-timeline-v2`). `POST /v1/commands` requires `Idempotency-Key` and typed multi-field `preconditions_json` (such as `charter_revision` and `expected_control_revision`), persists `conflicting_revision` denials in `command_receipt`, and scopes `GET /v1/commands/{command_id}` to the authenticated `(principal, operation)`. For `risk.resume`, preserve the two-phase boundary: observe the external venue cut outside the write transaction, then re-verify lineage and commit inside `BEGIN IMMEDIATE`.
- **Native Board Client (`apps/board/`):** The [native desktop Client](../client/build.md) (Zig + Native SDK 0.11.1) consumes only the versioned control-plane contract, never the SQLite store and never per-click CLI spawning. Its internal transport adapter (direct UDS vs a single persistent local stdio bridge) and local pending-receipt store are gated on a pre-Stream-B2 Native SDK 0.11.1 capability probe. Separate **Data State** from **Link State** so routine refreshes and transient disconnects never blank-wipe the last verified projection while locking mutations fail-closed. The client's `board-pending` file stores **only already-transmitted unknown requests** for `GET /v1/commands/{command_id}` lookup, never offline queued mutations for automatic replay.
- **Agent (Two-Plane Harness):** The [harness](../employee/agent/harness/protocol.md) enforces two strict planes. The trusted **Outer Capability Broker** binds `run_id`, `company_id`, `agent_id`, `fencing_token`, capability scope and budget ceiling server-side and mediates every company tool call with atomic receipts. The **Inner Sandboxed Desk** runs workspace tools under the Agent's pinned immutable `sandbox_backend` (local macOS, no automatic fallback), permitting R/W only inside the per-Agent Desk and per-run scratch directories with zero outbound network egress and unreadable company SQLite store and credentials. SQLite `private_desk` remains metadata and revision authority. Desk content, provider output and connector responses are data, not grants. No SDK hook, prompt, Client setting or company program can bypass admission. Bind paper execution separately from price data; never fall back to a live destination.

## One owner per fact, one commit per local transition

| Transition | Commit boundary | What stays outside |
| --- | --- | --- |
| [Found company](../company/systems/organization/found-company/bootstrap/spec.md) | Company, founder, grant, first duty and founding receipt together. | Opening an existing store is not founding. No model call or account creation in this transaction. |
| [Admit order](../company/profiles/quant/trading/admit-intent/reserve/spec.md) | Under account serialization, check scope and limits; commit frozen terms, submission identity, outbox row and subledger reservation together. | Dispatch only after commit. Never hold a write transaction during a model, network or venue call. |
| [Book fill](../company/profiles/quant/fund-books/book-fills/post/spec.md) | Only the subledger posts the identified fill, fee and remaining reservation, and records the pending accounting source together. | The destination owns fill and position evidence; the company may retain immutable observations for work and accounting. The [general-ledger bridge](../company/profiles/quant/fund-books/book-fills/journal-source/spec.md) delivers the source separately; a late accounting receipt cannot trigger another order. |

Enforce identities with scoped unique keys and relationships with checked foreign keys on every store connection. Compare immutable terms on replay, not just the key. Exact prices, amounts and quantities carry units and representable precision; reject ambiguous inputs before dispatch. Preserve source time and first availability separately when a decision uses dated evidence. Logs, balances cached by Risk, and Client projections are not alternative books.

**Example:** after the destination acknowledges an order, the company loses the reply. Retain the reservation and look up the original submission identity; a timeout is neither a rejection nor permission to send again. Two deliveries of the same fill must leave one posting. A different fill under the same order is not a duplicate. These are local correctness rules, not a claim that the later crash drill passed.

## Change, operate and verify

| Concern | Decision and evidence at the point of change |
| --- | --- |
| Data and release compatibility | Stamp the company store with its identity, `schema_migrations` entries and `PRAGMA user_version` at founding. Refuse a missing expected store or future `user_version` before scheduling work. Before each schema upgrade, the storage owner supplies an ordered SQL migration, a WAL-normalized checkpoint (`journal_mode=DELETE`, zero sidecars) and an upgrade test from the last supported revision. Reopen it and compare identity, logical watermark, outstanding work and economic records. Roll back a binary only if it can read **and safely write** the effective schema; never rewind external effects by restoring an old file. [Restore contract](../company/systems/operations/restore-company/restore/spec.md) |
| Bounded operation | Start with one company, founder, paper account and instrument in the acceptance run. Give each turn a deadline, turn cap and authorized spend limit; bound store waits and connector attempts. At the bound, retain the duty or unresolved effect; do not spin, spawn another worker or retry an uncertain write. Revisit concurrency or process placement only when measured queue age or lock waits violate a duty's declared bound. |
| Diagnosis and data handling | Correlate company, Agent, duty/run, fencing token, action, destination order/fill and booking receipt. Report the last completed step, reason and next owner; absence of a receipt is not success. Log identifiers, revisions, timing and dispositions; **never log hidden model reasoning, secrets or raw private Desk contents**. Context compaction and tool-output offloading must **never evict open-effect receipts or active grant checks**. Diagnostic logs may expire; they must not be the only copy of a receipt needed to settle a duty or the books. |
| Dependencies and code quality | At first use or upgrade, the adapter owner verifies the pinned release's public interface and runs the smallest contract test against it. A fixture verifies the consumer, not the installed SDK. Reuse the company interface across paper, replay and authorized external modes, not the destination binding or assumptions about fills. Do not add a framework for a hypothetical second deployment. |

**Review the change, not a universal checklist.** For each unit, name the changed owner and consumer, one invariant it must preserve, and the observation that would disprove it. A schema or public-contract change also names its compatibility path. Reuse the owning spec and PR; do not create a parallel design record.

**Order of proof:** deterministic CI checks the changed transition; the integrated [first-trade Goal](flow-delivery/goal-01-04.md) additionally needs one actual Agent request → independent paper fill → booked position on the same candidate. Subsequent shifts and fault recovery, measured net return, then comparison with the incumbent and separate RSI evaluation stay in their [own milestones](development-roadmap.md). A green test or profitable trade alone proves none of those later claims.
